# ADR-0012: Connect for gRPC-Web, grpc-gateway for partner REST

## Status
Proposed

## Date
2026-08-11

## Context

The stack requires both REST and gRPC. Browsers cannot speak native gRPC — HTTP/2 trailers
are not exposed to JavaScript — so a browser client needs gRPC-Web or an equivalent.

The traditional answer is Envoy as a `grpc-web` translating proxy. That adds a network hop,
a second piece of infrastructure to configure and operate, and a component in the critical
path of `PushEvents` — the one endpoint that must never be the reason a store cannot sync.

## Decision

**Connect (`connectrpc.com`)** for the browser client, served directly by the Go server.

- One Go handler serves three protocols on the same endpoint: gRPC, gRPC-Web, and Connect's
  own HTTP/JSON protocol. No proxy, no sidecar, no translation hop.
- The TypeScript client is generated by `buf.build/connectrpc/es` from the same protos.
- Connect's JSON protocol makes every RPC callable with `curl`, which is a real
  debugging benefit during an incident.

**grpc-gateway** additionally generates a conventional REST surface from `google.api.http`
annotations, for third-party integrations that expect resource-shaped URLs.

Both are generated from the same `.proto` files. REST is a second encoding of one API, not
a second API.

## Alternatives Considered

### Envoy as a gRPC-Web proxy
- Pros: the standard, battle-tested approach; decoupled from the application.
- Cons: an extra hop and an extra operational component in the sync critical path; Envoy
  configuration is a specialism; a misconfiguration becomes a store-level outage.
- Rejected: Connect removes the component entirely.

### REST-only, no gRPC for the client
- Pros: simplest; universally debuggable.
- Cons: gives up streaming, which `PullChanges` uses for large deltas and first-sync
  progress; gives up binary encoding on the highest-volume endpoint.
- Rejected: streaming pull is a genuine requirement, not a preference.

### `grpc-web` official client plus Envoy
- Pros: reference implementation.
- Cons: the generated TypeScript is dated compared with `@bufbuild/protobuf`; still needs
  the proxy.
- Rejected.

### tRPC
- Pros: outstanding TypeScript ergonomics.
- Cons: TypeScript-only. The server is Go. It also cannot describe the event payloads
  persisted in Postgres.
- Rejected: incompatible with the stack and with [ADR-0002](0002-protobuf-buf-contracts.md).

## Consequences

- No proxy in the client-to-server path. Fewer components, fewer failure modes, one less
  thing to misconfigure during an incident.
- Server-streaming works in the browser over HTTP/2 for `PullChanges`.
- Every RPC is `curl`-able via the Connect JSON protocol, which materially helps debugging
  and support.
- Two generated client stacks exist (Connect-ES for our client, grpc-gateway REST for
  partners). Both derive from one proto, so they cannot drift semantically — but the REST
  surface is generated rather than designed, and Protobuf's JSON mapping of `oneof` and
  well-known types is not always what a REST-native partner expects.
- Connect is a smaller ecosystem than grpc-go, though it is maintained by Buf, which is
  already a core dependency. That concentration of dependency on one vendor is worth noting
  explicitly.
- If the REST surface becomes a product in its own right, it deserves a hand-designed
  façade rather than more annotations.
